# Acta 0.3.0 — preparación de release

**Preparación, no publicación.** No se crea tag, GitHub Release ni imagen de contenedor. La referencia publicada anterior es [v0.2.0](https://github.com/ruzer/Acta/releases/tag/v0.2.0), commit `8482cea17a2337106c9c50508cade65ee3d76233`.

## Base y alcance

El [PR #11](https://github.com/ruzer/Acta/pull/11) incorporó operaciones por lote. El [PR #12](https://github.com/ruzer/Acta/pull/12) incorporó el simplicity pass y se fusionó conservando sus commits originales con DCO:

- `18987d7c0d8fd8d13b5bb72b30103890a862eb83`: correcciones y tests.
- Main tras PR #12: `6a2c5a47405779fa1b8ac2d959bd0541b46c9f94`.

Ese main tiene el mismo árbol que el head probado de PR #12. Su [CI post-merge](https://github.com/ruzer/Acta/actions/runs/37481727127) completó **verify, secrets y selfhosting: PASS** el 2026-10-06. No se sustituyó esa ejecución por los checks del PR.

El PR de preparación `release/v0.3.0` modifica únicamente versiones, referencias internas de paquetes y documentación. El commit final de publicación deberá tomarse del main resultante de ese PR y comprobarse de nuevo contra su propio CI. Ninguna marca de versión en package.json equivale a publicación.

## Decisión SemVer

Se recomienda **0.3.0**, no 0.2.x. La [política de Acta](../RELEASING.md#política-de-versiones) reserva PATCH para correcciones compatibles y MINOR para funcionalidad compatible nueva. Las operaciones por lote incorporan seis endpoints de preview/confirm para área, participantes y publicación, manteniendo los contratos individuales. El simplicity pass suma correcciones y orientación, pero el alcance conjunto excede un parche.

[SemVer 2.0.0](https://semver.org/lang/es/) considera 0.y.z desarrollo inicial. Acta adopta esta convención de incrementos sin prometer estabilidad absoluta antes de 1.0. No se identificó un cambio incompatible en el delta revisado: no se eliminan contratos individuales, no cambian enums de dominio, formato de importación, esquema/migraciones ni configuración Docker/storage. Las nuevas operaciones conservan autorización y controles de concurrencia existentes.

Raíz, frontend, backend, contracts, sus dos dependencias internas y las siete entradas correspondientes del lockfile quedan en **0.3.0**. No se cambian resoluciones, integridades ni versiones de dependencias externas en el PR de preparación.

Se inspeccionaron los resultados y cobertura por caso; [informe y limitaciones](../usability/SIMPLICITY-PASS.md#validación-reproducible-y-resultados). El workflow actual no ejecuta Playwright: sus 40 casos son evidencia local, no se atribuyen al CI.

El PR de versión exige `npm ci` y los mismos tres checks sobre sus propias versiones. Dado que no cambia fuente funcional ni dependencias externas, el Playwright completo del árbol funcional se conserva como evidencia equivalente; no se reinicializan otras instalaciones para repetir pruebas destructivas sin un cambio que lo justifique. El CI de main después de fusionar la preparación debe quedar verde antes de declarar listo el candidato.

## Actualización y límites

No hay nueva migración ni cambio de provider respecto de v0.2.0. Esto no elimina la obligación de backup coordinado y ensayo en staging: seguir [Self-hosting](../SELF-HOSTING.md#actualizar) y [Backup/restore](../BACKUP-RESTORE.md). La prueba de restart del CI no sustituye un nuevo ensayo de restore; aquí no se afirma haberlo repetido.

VersityGW sigue como provider self-hosted predeterminado; no se amplía la matriz de compatibilidad S3. Las limitaciones de plataformas/providers permanecen en [S3-PROVIDERS](../S3-PROVIDERS.md). No se afirma HA ni rendimiento universal a partir de la muestra local.

Deuda conocida no bloqueante para este alcance: retención de selección entre operaciones, distinción en bandeja de aclaraciones ya respondidas, densidad de advertencias antes de asignar y advertencia de tamaño de chunk de Vite. Los recorridos de agentes no demuestran usabilidad sin capacitación para personas humanas.

## Downstream

Los forks institucionales y demás downstream **no deben actualizarse desde main todavía**. Deben esperar a la publicación explícita del **tag y release v0.3.0**. Ese tag será una nueva base candidata, sujeta a verificación del commit, revisión de personalizaciones y pruebas en una rama propia. Esta preparación no modifica ningún downstream.
